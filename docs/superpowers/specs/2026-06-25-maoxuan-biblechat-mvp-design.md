# 毛选 BibleChat MVP 设计

## 概述

把 Red Wisdom 打造成一个“毛选与毛泽东思想版 BibleChat”。MVP 保留当前 Red Wisdom 的视觉语言：红色、暖米色宣纸质感、毛选氛围、抽卡仪式感，以及宋体/书法字体搭配。产品结构升级为类似 BibleChat 的体验：用户可以询问现实生活中的问题，获得带原文出处的咨询与安慰，也可以直接回到原著阅读，并通过每日陪伴钩子持续回来。

第一版优先保证“方法论稳定”和“引用可信”，而不是追求功能大而全。系统应先把毛选蒸馏成一组可调用的回答 skills，例如主要矛盾分析、调查研究、实践验证、群众路线、批评与自我批评、持久战耐心等。用户提问后，产品先选择合适的 skills 来组织回答，再从现有毛选 Markdown 语料中检索相关原文段落作为支撑。AI 回答应以方法论咨询、心理安慰和可执行行动建议为主，并展示清晰出处与回到原文的链接。

## 目标

- 帮助用户把真实焦虑、决策、工作、学习、关系、自律等问题带到一个毛选风格的方法论顾问中。
- 把毛选蒸馏成一套可复用的“方法论 skills”，让回答有稳定结构，而不是每次完全依赖模型临场发挥。
- 让回答基于本地毛选原文段落，而不是只依赖模型记忆。
- 保留从回答回到原文的清晰路径：每次回答展示引用摘录，并能打开对应原文文章。
- 把每日卡片/每日提问保留为有趣的留存钩子，引导用户继续提问和阅读。
- 在现有静态站点 + Vercel 风格代码结构内交付完整 MVP，不引入账号、支付、云同步或重型框架。

## 非目标

- MVP 不做用户登录、个人云端历史或多设备同步。
- 不做模型微调，也不接外部向量数据库。
- 不宣称助手是权威政治、医疗、法律或临床心理健康顾问。
- 不做完整学习计划系统，只保留简单每日提示/卡片入口。
- 不改成 BibleChat 的视觉身份；BibleChat 只作为产品结构参考。

## 产品结构

### 1. 问道：现实问题咨询

主页面升级为更有目的性的“问道毛选”体验。用户可以用自然语言描述一个真实问题。回答格式应保持一致：

1. **先稳住**：用一小段安慰性重述接住用户的问题。
2. **调用方法**：选择 2-3 个毛选 skills，例如“抓主要矛盾”“先调查再判断”“用实践检验”“争取多数支持”。
3. **从原文看**：给每个关键 skill 配 1-2 段检索到的毛选原文，并标注文章标题。
4. **怎么做**：把 skills 转成未来一天或一周内可以执行的具体行动。
5. **回到实践**：用一个小实验或反思问题收尾。

当检索上下文较弱时，助手应避免装作很确定。如果本地搜索没有找到强相关材料，回答可以先使用已蒸馏的通用方法论 skills，但必须说明“本次原文匹配较弱”，并邀请用户补充更多细节。

## 毛选方法论 Skills

问道毛选的回答核心不是单纯“搜原文”，而是把原文长期沉淀成一组可调用的方法论 skills。MVP 先内置一组静态 skills，每个 skill 包含名称、适用场景、回答角度、行动模板和支撑关键词。AI 回答时必须先选择 skills，再组织咨询。

第一版建议内置以下 skills：

- **抓主要矛盾**：适用于混乱、焦虑、选择困难、问题太多时。帮助用户找出当前最核心的矛盾和最小突破口。
- **没有调查就没有发言权**：适用于信息不足、脑补过多、对人或事判断过快时。引导用户先收集事实、访谈相关人、写下证据。
- **实践是检验真理的标准**：适用于想太多、迟迟不行动、完美主义时。把判断变成小实验，用行动反馈修正认知。
- **实事求是**：适用于自欺、幻想、过度悲观或过度乐观时。把愿望、情绪和事实分开。
- **群众路线/从反馈中来**：适用于团队协作、产品、沟通、关系问题。引导用户从真实反馈中总结，再回到实践中验证。
- **持久战与战略耐心**：适用于长期目标、学习、减肥、职业转型、压力积累时。帮助用户把问题拆成阶段，不用一时成败判断全局。
- **批评与自我批评**：适用于被批评、内疚、关系冲突、复盘失败时。把批评从羞耻感中拆出来，转为修正机制。
- **统一战线/团结可团结的人**：适用于资源不足、推进困难、需要协作时。帮助用户识别同盟、争取支持、减少无谓对抗。

每个 skill 不应变成空洞口号。它必须输出：

- 当前问题中它要处理的矛盾；
- 用户可以马上做的一步；
- 一条来自原文或原文检索结果的支撑；
- 一个回到实践的验证动作。

### 2. 读原著：原文阅读与出处追踪

现有阅读页继续作为原文库。它需要支持从 AI 引用跳转过来：

- `reading.html#<encoded filename>` 打开对应文章。
- 聊天里的引用卡片展示文章标题、短摘录和“读原文”操作。
- MVP 只跳转到文章级别；精确段落高亮留到后续扩展。

阅读器继续保留目录导航和上一篇/下一篇导航。

### 3. 每日陪伴

当前抽卡仪式从“整个产品”转为每日陪伴钩子：

- 首页展示“今日一问”或“今日方法”卡片。
- 用户抽卡后，可以选择“带着这个问题去问道”或“读相关原文”。
- 每日提示应关联常见问题：焦虑、行动迟滞、被批评、自律、工作压力、学习和关系。
- 这个钩子可以有趣、有仪式感，但要把用户导向带出处的聊天和原文阅读。

## 推荐 MVP 方案

在 AI 调用前加入“skill 选择 + 本地词法检索”流程：

1. 建立 `data/mao-skills.json`，把毛选方法论蒸馏成静态 skill 列表。
2. 基于现有 `data/catalog.json` 和 `data/articles/*.md` 构建来源索引。
3. 把文章切成段落级 chunk，并保留元数据：
   - 文章标题
   - 文件名
   - 卷名
   - chunk 文本
   - 粗略段落序号
4. 根据用户问题选择 2-3 个相关 skills：
   - 用用户问题和 skill 的适用场景、关键词、行动模板做词法匹配
   - 对焦虑、行动、批评、团队、长期目标等常见问题做轻量规则加权
   - 允许用户后续手动切换或补充 skill，但 MVP 先自动选择
5. 使用适合中文的简单词法评分搜索 chunk：
   - 用中文双字组合和有意义的 ASCII 单词做 token
   - 提升查询词精确匹配权重
   - 提升被选中 skills 的关键词权重，例如 `矛盾`、`实践`、`调查`、`群众`、`路线`、`主要`、`次要`、`困难`、`批评`、`学习`、`工作`
6. 将选中的 2-3 个 skills 和得分最高的 4-6 个原文 chunk 一起发送到 `/api/chat`。
7. 服务端调用 OpenRouter，并使用系统提示词要求模型按照 selected skills 组织回答，只用传入的 contextChunks 做原文支撑。
8. 浏览器接收流式回答，并展示所用 skills 和引用元数据。

为了速度和稳定性，如果浏览器逐篇拉取 Markdown 太慢，开发阶段预生成一个紧凑 JSON 索引。MVP 可以生成 `data/search-index.json`，因为原文语料是静态的。

## 架构

### 需要保留的现有文件

- `index.html`：首页和抽卡仪式。
- `chat.html`：聊天 UI，将升级为主要咨询界面。
- `reading.html`：原文阅读器，继续作为原文库。
- `api/chat.js`：Vercel serverless OpenRouter 代理。
- `data/catalog.json`：文章目录。
- `data/articles/*.md`：原文语料。
- `data.js` 和 `data/quotes.json`：语录/卡片数据。
- `assets/*` 和 `style.css`：当前视觉系统。

### 新增或修改的模块

- `data/search-index.json`：生成后的原文 chunk 检索索引。
- `data/mao-skills.json`：蒸馏后的毛选方法论 skills。
- `scripts/build-search-index.mjs`：从目录和 Markdown 文件生成 `search-index.json`。
- `retrieval.js`：如果在客户端检索，则放浏览器侧检索工具函数。
- `chat.html`：升级布局、回答渲染、引用卡片和每日提示快捷入口。
- `api/chat.js`：接受 `{ message, history, selectedSkills, contextChunks }`，把选中的 skills 和检索上下文注入 OpenRouter prompt，并流式返回回答。
- `index.html` 和 `script.js`：让抽卡流程导向聊天，并修复现有 `saveIcon` 运行时错误。

最简单的 MVP 可以把 skill 选择和检索都放在浏览器端运行，避免 Vercel 服务端文件系统假设。浏览器加载 `data/mao-skills.json` 和 `data/search-index.json`，本地选择 skills 并排序 chunks，只把 selected skills 和 top chunks 发送到 `/api/chat`，并渲染同一组 skill 卡片与引用卡片。这样服务端代码更小、更透明。

## 数据流

### 聊天查询

1. 用户在 `chat.html` 输入现实问题。
2. 浏览器加载一次 `data/mao-skills.json` 和 `data/search-index.json`，并缓存在内存里。
3. 浏览器根据用户问题选择 2-3 个毛选 skills。
4. 浏览器根据用户问题和 selected skills 给原文 chunk 排名。
5. 浏览器展示“正在选择方法”和“正在查找原文”状态，然后显示选中的 skill 卡片与来源卡片。
6. 浏览器向 `/api/chat` POST：
   - 用户问题
   - 对话历史
   - 选中的 skills
   - 选中的来源 chunk 和元数据
7. 服务端注入严格的 skill-first + context-backed prompt，并调用 OpenRouter。
8. 浏览器流式展示回答，并把 skill 卡片和引用卡片附在回答下方。
9. 用户可以点击任意引用卡片上的“读原文”。

### 每日卡片到聊天

1. 用户在 `index.html` 抽卡。
2. 卡片展示语录或方法提示。
3. 用户选择 CTA：
   - “带着这个问题去问道”打开 `chat.html?prompt=<encoded prompt>`。
   - “读相关原文”在已知来源时打开 `reading.html#<filename>`。
4. 聊天页预填提示词，让用户自己点击发送，这样过渡更有意图感，不会显得突兀。

## Prompt 要求

AI 系统提示词应要求助手：

- 语气温暖、稳定、偏方法论；
- 可以少量称呼用户为“同志”，但不要每段机械重复；
- 使用毛选中的方法论概念，例如矛盾分析、实践、调查研究、群众路线、实事求是；
- 必须优先使用请求中提供的 selected skills 组织回答；
- 让观点基于提供的原文摘录；
- 区分原文引用和自己的解释；
- 避免编造文章标题、日期或直接引文；
- 给出可执行的下一步行动；
- 当用户表达自伤、危险或危机信号时，先用支持性语言鼓励立刻寻求现实中的可信任人员或专业帮助，再进行方法论分析。

回答不应假装是毛泽东本人在说话。定位应是“用毛选方法论进行分析”，而不是角色扮演一个仍在世的个人顾问。

## UI 设计

### 视觉语言

保留当前配色和材质：

- 中国红用于主要操作和重点强调；
- 暖米色宣纸背景；
- 深墨色正文；
- 使用现有素材中的轻微纸张/卡片纹理；
- 在已有位置继续使用毛主席画像素材；
- 展示标签用克制书法感字体，正文用可读性强的衬线字体。

避免把应用做成通用 SaaS 仪表盘。它应该像一个“阅读室 + 咨询案头”：冷静、严肃、温暖，并带一点仪式感。

### 聊天页

聊天页应包含：

- 顶部导航，能回首页和阅读页；
- 一个紧凑介绍区，说明回答基于检索到的原文；
- 常用场景 prompt chips，例如：
  - “我最近很焦虑”
  - “工作推进不下去”
  - “被批评后很受挫”
  - “如何开始行动”
- 流式回答区域；
- 每条回答使用到的 skill 卡片；
- 每条助手回答下方的引用卡片；
- 当 API key 缺失、检索失败或模型调用失败时，有清楚的错误状态。

### 首页

首页仍以抽卡仪式开场，但卡片揭晓后提供：

- “问问这件事”
- “读相关原文”
- “再抽一次”

旧的保存卡片代码要么完整恢复，要么删除。MVP 中除非明确恢复图片保存，否则应移除已经损坏的保存引用。

### 阅读页

阅读页需要支持现有目录浏览和从引用卡片跳转到文章。如果时间允许，从聊天打开时可以展示一个小提示：“来自问道引用：<article title>”。

## 错误处理

- 如果 `search-index.json` 加载失败，展示非阻塞警告；如果 `mao-skills.json` 已加载，可以继续基于 skills 回答，但必须明确标注“本次缺少原文检索支撑”。
- 如果 `mao-skills.json` 加载失败，展示明确错误，并禁用“问道”回答，因为 skills 是问道毛选的核心能力。
- 如果检索结果弱，把引用标记为“相关参考”，并请用户补充更多细节。
- 如果 `/api/chat` 返回缺少 API key，展示可操作的配置提示。
- 如果 OpenRouter 中途失败，保留用户消息和已选引用，方便重试。
- 如果用户消息暗示自伤或即时危险，先用支持性语言鼓励立刻寻求现实帮助，再做任何方法论分析。

## 测试与验证

MVP 手动验证：

- `python3 -m http.server 8080` 能提供静态页面。
- `index.html` 抽卡流程不会抛出 `saveIcon` 错误。
- `chat.html` 能加载 `search-index.json`，检索来源卡片，并把 top chunks 发送到 `/api/chat`。
- `chat.html` 能加载 `mao-skills.json`，为常见问题选择合理 skills。
- 聊天回答能流式展示 Markdown 和引用卡片。
- 聊天回答能展示本次使用的 skills。
- 引用的“读原文”能打开 `reading.html` 中的预期文章。
- `reading.html#016-实践论.md`、`reading.html#017-矛盾论.md`、`reading.html#026-论持久战.md` 能正确加载。
- 缺少 API key 时展示清楚错误。
- 移动端宽度下，导航、输入框和卡片可用，文字不重叠。

可行时加入自动检查：

- 运行索引构建脚本，并断言它为所有目录文章生成 chunk。
- 校验每条生成引用的文件名都存在于 `data/articles`。
- 校验 `data/mao-skills.json` 中每个 skill 都包含名称、适用场景、关键词和行动模板。
- 对 `焦虑`、`行动`、`批评`、`调查研究`、`主要矛盾` 等查询运行简单检索冒烟测试。

## MVP 验收标准

- 用户可以提出一个现实问题，并收到基于 2-3 个毛选 skills 组织的回答。
- 在找到相关段落时，回答带至少两个来源卡片。
- 每个选中的 skill 都有清楚的用途说明和行动建议，不只是口号。
- 每张来源卡片都有文章标题、摘录和可用的“读原文”链接。
- 每日卡片体验能自然导向聊天或阅读。
- 应用保留 Red Wisdom 的视觉身份。
- 首页翻牌流程中的已知错误被修复。
- README/部署说明更新到足够清楚，不再误导本地运行和 Vercel 使用方式。

## 后续扩展

- 用户账号、历史记录、收藏和笔记。
- 阅读页精确高亮被引用段落。
- 使用 embedding 或本地向量索引提升检索质量。
- 主题课程：矛盾、实践、调查研究、群众路线、批评、自律。
- 每日 streak 和个性化实践计划。
- 更严格的来源 QA 层，拒绝没有原文支持的生成引用。
